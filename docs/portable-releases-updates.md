# Windows portable и ручные обновления — D042/D065

2026-10-28. Ручной клиент, диалог, подготовка новой версии и нативный помощник реализованы локально по поручению пользователя. Сетевые сценарии, упаковочный формат и протокол переключения проверены на Linux; применение настоящего комплекта и Schannel на Windows ещё требуют проверки. D051 сохраняется: без push, PR, тегов и публикации. CI ранее упрощён по D042.

## Путь пользователя

1. **Справка → Проверить обновления…** открывает одно немодальное окно и запускает проверку. Повторная команда поднимает это окно; работа с деталью остаётся доступной. До команды запросов нет.
2. Окно показывает установленную версию, доступный выпуск и его изменения либо отдельное состояние: новых версий выбранного канала нет, релизов нет, ошибка сети. Текст выпуска показывается без исполнения HTML/внешних изображений. Предварительные версии включены по умолчанию, если сама установленная версия предварительная. Смена флажка требует кнопки проверки и сама запрос не отправляет.
3. Для Windows portable основное действие — **Обновить и перезапустить**. Скачивание и подготовка выполняются с прогрессом и отменой. Дополнительно доступны страница выпуска и **Скачать ZIP отдельно…**. Для Windows-сборки вне поддержанного комплекта предлагается только отдельный ZIP; для Linux — страница выпуска с пояснением платформы.
4. До выхода проверяются размер/SHA-256 ZIP, пути, состав, версия и архитектура распакованной программы. Ошибки и отмена оставляют текущую программу открытой. Длительная файловая проверка работает отдельно от CAD-worker.
5. После подготовки программа ожидает текущую CAD-операцию. При изменённом проекте предлагает **Сохранить / Не сохранять / Отмена**, по умолчанию сохранение. Используется существующее асинхронное сохранение захваченного документа; отмена диалога, ошибка или оставшиеся изменения запрещают перезапуск. Настройки синхронизируются до выхода; ошибка записи также блокирует его.
6. Помощник запускается до нормального закрытия приложения, но ждёт завершения его процесса, включая worker. Затем переключает комплект и открывает сохранённый `.bend` либо исходный STEP. Отказ от сохранения означает осознанную потерю несохранённых параметров после закрытия; ошибка запуска помощника их не сбрасывает в работающем окне.

**Автопроверки на старте, суточного таймера, фонового опроса, автоматического скачивания нет.** Таймауты запросов, прогресс и подтверждение запуска относятся только к уже начатой пользователем операции. Закрытие диалога отменяет сетевую/подготовительную работу и ожидающий перезапуск; уже начатое сохранение проекта завершается обычным образом.

## Формат комплекта и восстановление

Новый ZIP имеет один корневой каталог:

```text
3d-bending-simulator.exe          нативный запускатель без Qt/OCCT, protocol 1
portable-format.txt             1
current.txt                     активная версия
README.txt
runtime/<VERSION>/
  bin/3d-bending-simulator.exe   приложение, Qt/OCCT DLL и плагины
  share/                        ресурсы, примеры, лицензии
  VERSION
  runtime-manifest.json         имена, размеры и SHA-256 файлов
  .ready                        отметка готовности этой версии
data/settings.ini               создаётся локально, в ZIP отсутствует
.updates/                       локальные staging/lock/journal/ack/helper
```

Ярлык указывает на **EXE в корне**, а не на EXE конкретной версии. Стабильный запускатель выбирает runtime до загрузки Qt/DLL. Программа переносит прежние системные настройки в `data/settings.ini` только при отсутствии этого INI; прежние настройки не удаляются. Существующий INI не затирается. Пути к личному каталогу инструмента остаются прежними: перенос комплекта на другой ПК не переносит сам частный каталог автоматически.

Проверенный runtime копируется в уникальную `.updates/incoming-*` на том же томе, каждый файл проверяется при записи. После завершения каталог переименовывается в `runtime/<VERSION>`. Одинаковая уже подготовленная версия повторно используется только при совпадении манифеста и хешей управляемых файлов. Существующие каталоги версий не перезаписываются; неизвестные пользовательские файлы в них не удаляются. Отмена на границе завершения может оставить готовый неактивный runtime, но не меняет `current.txt`.

Копия нативного запускателя в `.updates` ждёт выхода родителя до 120 секунд. Межпроцессная файловая блокировка сериализует переключение и обычный запуск во время этой транзакции; ОС освобождает блокировку после сбоя. Помощник записывает журнал old/new/token, атомарно меняет `current.txt`, запускает новый EXE. Только видимое главное окно с готовым OCCT viewer подтверждает запуск; новый процесс проверяет корень/версию/токен и записывает ack. Помощник ждёт до 30 секунд.

При раннем завершении новой версии восстанавливается указатель и запускается старая. Если новый процесс ещё жив, но не подтвердил готовность, он **не завершается принудительно**: указатель восстанавливается для следующего запуска, пользователь видит объяснение. При прерывании помощника следующий обычный запуск сначала читает журнал: подтверждённый готовый runtime сохраняется, неподтверждённый заменяется предыдущим указателем. При противоречивом/повреждённом журнале запускатель сообщает ошибку и не удаляет данные. Проверка готовности не доказывает отсутствие будущих ошибок новой версии.

Старые runtime, помощники и следы незавершённого staging автоматически не удаляются. Это осознанное ограничение первого механизма: обновлению нужно место для старой и новой версии, временного ZIP и распаковки. Проекты рекомендуется хранить вне `runtime`/`.updates`; `data`, `.bend`, STEP и частные каталоги не входят в обновляемый набор.

**Запускатель protocol 1 сам не заменяется**: обновляется полный payload приложения, а неизменяемый нативный bootstrap остаётся совместимым с этим протоколом. Если потребуется исправление/несовместимый протокол запускателя, нужен полный новый ZIP в отдельной папке. Старый опубликованный `2026.1.0-alpha.1` не имеет клиента/этого формата: переход на первый новый комплект также выполняется вручную, последующие совместимые версии — из программы.

## Источник и целостность

Источник фиксирован: публичные GitHub Releases `DenisPapushaJava/3d-bending-simulator`. Ключи и учётная запись не нужны. Клиент читает список постранично, включая prerelease; до 20 страниц по 100. Превышение/ошибка страницы — ошибка проверки, а не утверждение актуальности.

Принимаются только опубликованные нечерновые `vYYYY.RELEASE.PATCH[-alpha.N|-beta.N|-rc.N]`, согласованные с флагом prerelease. Сравнение числовое: `alpha.10 > alpha.2`, `alpha < beta < rc < stable`; предложение только строго новее установленного. `sdk-*`, чужие теги, source ZIP и dependency-sources не выбираются как приложение.

Имя asset — `3d-bending-simulator-<VERSION>-windows-x86_64.zip`, uploaded; рядом обязателен `SHA256SUMS.txt`. Проверяются один соответствующий checksum, точный размер и SHA-256; при наличии GitHub digest он также должен совпасть. ZIP пишется через временный атомарный файл. SHA-256 подтверждает целостность относительно релиза, **не является цифровой подписью издателя**; доверие основано на HTTPS и нашем репозитории.

Исходные адреса assets ограничены точным путём выпуска этого репозитория. Разрешены до пяти HTTPS-перенаправлений на `github.com`, `api.github.com`, `release-assets.githubusercontent.com`, `objects.githubusercontent.com`; произвольные URL из JSON не используются. Есть таймауты, ограничения JSON/ZIP/распакованного объёма, явная ошибка rate limit, без автоматических повторов. CAD/проект/настройки в запросы не включаются; сервер получает обычные сведения HTTPS/HTTP, User-Agent с версией приложения.

Собственный PowerShell-скрипт использует системный Windows PowerShell/.NET ZipArchive без выполнения файлов архива. Он исключает абсолютные/выходящие пути, ADS, Windows reserved names, ссылки/специальные файлы и совпадения без учёта регистра. Лимиты: ZIP/отдельный файл до 1 GiB, распакованный объём до 2 GiB, до 20 000 записей, ограничение степени сжатия. Проверяется манифест protocol 1, Windows x86_64 и PE-заголовок основного EXE. Это не проверка работоспособности DLL: её выполняют отдельные пробы комплекта и запуск новой программы.

## Модули, TLS и поставка

`application/ReleaseVersion` — чистый C++ без Qt/OCCT. `update/Bending::Update` — Qt Network/JSON/файлы/подготовка, отдельный ограниченный I/O-worker. `ui/UpdateDialog` отображает состояния; MainWindow использует прежний контроллер сохранения/завершения. Конкретный клиент создаёт `app`; его конструктор запросов не делает. Тестовый loopback origin передаётся только из тестового executable, production CLI/env для подмены источника нет.

Windows включает Qt Network и **Schannel TLS backend**, OpenSSL backend не поставляется. `--update-runtime-probe` проверяет наличие TLS/Schannel без сети; упаковщик проверяет и payload, и root launcher при очищенном SDK PATH. Qt Network/Schannel входят в уже сохраняемые исходники qtbase и их notices. PowerShell/.NET являются системными компонентами, не вкладываются в ZIP. [Лицензии](licensing.md).

Упаковщик сохраняет `--no-compiler-runtime`: Microsoft Visual C++ x64 Runtime остаётся предпосылкой GUI. Только нативный bootstrap собран со статическим CRT. Нельзя объявлять комплект полностью автономным от MSVC Runtime. Не меняются версия Qt/OCCT/vcpkg и SDK-cache; формат поставки/Qt DLL inventory меняются.

CI D042: quality + Windows/Linux Release/тесты, только Windows assets/исходники/checksums по тегу, draft-only. Новый обязательный внешний сервис/фоновая задача не добавляются. Реальное выполнение этого CI отложено по D051.

## Проверки и границы доказательств

Локально 2026-10-28: числовое сравнение версий в `core`; настоящий QNetworkAccessManager с локальным HTTP fixture (пагинация, каналы, неверные ответы/URL/hash, 429, таймаут, отказ подключения, отмена и повтор); немодальный GUI/защита сохранения; настоящий Qt-free launcher с дочерним fixture (активация, Unicode/кавычки, ожидание родителя, блокировка, ранний отказ, журнал/ack); упаковщик/манифест/хеши/отмена/сохранность data. Скрипт распаковки дополнительно выполнен через PowerShell 7 на Linux, включая небезопасные ZIP. Это не подтверждает Windows PowerShell 5/Win32/DLL/Schannel.

Через локальную Postman Simulation настоящий C++ клиент получил список → checksums → байты пакета и проверил SHA-256; внедрённые 429 и задержка дают ошибку вместо «актуально». Пакет fixture — учебные байты, не запускаемый Windows ZIP. Повторение/источник контракта — [контекст](../postman/simulations/github-updates.context.md). В штатном CTest живой GitHub и Postman не нужны.

До следующего Windows-релиза остаются: обе ОС штатного CI; распаковка финального ZIP в новую папку без SDK окружения; Schannel/font/startup probes; интерактивный Windows/GPU; обновление между **двумя разными версиями** с реальным `.bend`/настройками, отменой/ошибкой сохранения, ранним отказом нового EXE и восстановлением после прерывания. Старый опубликованный тег не перемещать, текущий VERSION не выдавать за новый опубликованный выпуск.
