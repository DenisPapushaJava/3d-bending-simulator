# Предподготовка следующего ручного гиба — D158

Дата: 2026-11-04. Статус: реализовано локально по прямому поручению пользователя. Исходная диагностика паузы — [viewport-performance.md](viewport-performance.md#пауза-между-ручными-шагами--диагностика-2026-11-04). Стек, форматы, VERSION, геометрические правила и охват проверок не меняются; D051 сохраняется.

## Поведение

При запуске воспроизведения ручного шага программа готовит следующий шаг в фоне. При автопереходе и начале следующего воспроизведения подготовка продолжается на один шаг вперёд. Для полного рассчитанного `BendRoute` это не нужно: его previews уже подготовлены.

Предподготовка не меняет кадр, выбранный шаг, подписи/результаты, камеру, входные параметры и editRevision. Она не включает `hasWork()`/`isPreparingDraft()`, не посылает `stateChanged`, не показывает окно или отдельную надпись. Текущая анимация и работа с интерфейсом продолжаются. Это не подтверждение всего порядка.

При воспроизведении ручного режима UI запускает её сразу. При ручном переходе на соседний шаг вперёд UI ждёт 180 мс после публикации нового шага и затем готовит один следующий. Прыжок через шаг, возврат назад и смена оснастки сами по себе подготовку не запускают. Новый выбор отменяет отложенный запуск. В обоих режимах пропускаются шаги с известной коллизией, диагностикой короткого инструмента или ошибкой отображения. При паузе, переходе из этапа гибки, возврате к исходнику и обнаруженной коллизии ненужная подготовка отменяется. Первый ручной шаг после заготовки остаётся холодным, если его не готовили при воспроизведении.

## Один путь вычисления и приёма

`ImportController` копирует полный `RouteDraftRequest` текущего принятого draft и увеличивает только `step`. Документ, DocumentRevision/EditRevision, builder, весь порядок/ID/цели/повороты/инструменты/секции/упоры и ручная толщина захватываются вместе. Новые поля DTO автоматически участвуют в полном сравнении запроса.

Фоновая работа вызывает тот же `buildRouteDraft` и прогревает его существующий CAD-кэш D082/D104, ограниченный четырьмя результатами. Результат фонового вызова не публикуется и не переносится в отдельный UI-кэш кадров. Остаются только данные задания для объединения повторных попыток; завершение сохраняет ссылку на них без глубокого копирования параметров в GUI.

При выборе шага выполняется обычный `prepareRouteDraft` и обычный worker/приём результата: проверяются источник, ревизии, токен, полный запрос, признаки unverifiedDraft, кадры/проверенные позиции, оснастка, упоры, станок/пол и длины инструмента. Готовый кэш ускоряет этот вызов, а не заменяет валидацию. Фоновая ошибка не портит текущий шаг; явный запрос сообщает ошибку обычным способом. Данные из повреждённого/непригодного результата не становятся сценой через предподготовку.

## Планирование, приоритет и отмена

Используется тот же единственный `cadImportWorker`, второго CAD-потока нет. В дополнение к прежнему foreground-заданию/заменяемому ожидающему допускаются одна активная спекулятивная работа и одно заменяемое ожидающее описание. Отдельной неограниченной очереди или набора всех будущих кадров нет; лимит CAD LRU остаётся четыре результата, это ограничение объектов, не байтов RAM.

| Действие | Поведение |
| --- | --- |
| Повторный запрос той же предподготовки | Объединяется по полному снимку, новая работа не ставится |
| Следующий шаг уже готов | Обычный worker читает CAD-кэш и проходит обычную проверку результата |
| Пользователь/таймер выбирает ещё готовящийся тот же шаг | Работа сохраняется; явный запрос ставится следом в том же worker и читает прогретый кэш, без отмены/повторного тяжёлого построения |
| Выбран другой шаг, начат импорт/сохранение/чертёж/другая foreground-задача | Ненужная активная предподготовка получает stop, ожидающая и подсказка завершения очищаются; явная работа получает приоритет |
| Изменились порядок/инструмент/параметры/ориентация/толщина или закрыта деталь | Прежняя предподготовка отменяется, старые входы не публикуются |
| Пауза/уход со сцены, когда подготовка уже обслуживает явный запрос | Отмена только спекуляции не прерывает prerequisite этого foreground-запроса; обычная инвалидизация/Cancel по-прежнему отменяет всё |
| Завершение программы | Stop обоих видов работы и ожидание того же worker; никаких terminate/detach |

У предподготовки отдельный `stop_source`; её callback не меняет флаги foreground-занятости. Поэтому позднее завершение фоновой работы не объявляет ещё выполняемый импорт или выбранный draft готовым. Snapshot-проверка ограничивает подсказку завершения текущими документом/ревизиями. Старый результат CAD может использоваться лишь по полному геометрическому ключу, а его публикация всегда принадлежит актуальному foreground-запросу.

При смене/закрытии документа и замене builder отмена предподготовки выполняется до очистки старого CAD-кэша. Иначе задача могла бы заново создать старый cache после сброса, до следующей проверки токена. Порядок stop → discard проверяется управляемым тестом; общая геометрическая блокировка CAD-адаптера не меняется.

Отмена кооперативная: непрерываемый вызов OCCT должен закончиться. Если при ускоренном показе расчёт не успел, остаётся ожидание нужного шага. При 10× время анимации может быть меньше времени подготовки; этот блок не ускоряет саму геометрию и не обещает исчезновения каждой паузы. Пропуска проверок или кадров с коллизиями нет.

## Проверки и измерения

`application.draft-prefetch` использует управляемый тестовый builder/cache и проверяет:

- незанятый GUI/неизменные текущий draft и уведомления при фоновой работе;
- объединение повторов, один ожидающий запрос при быстрой паузе/возобновлении;
- ранний переход к совпавшему запросу без отмены/повторного тяжёлого построения;
- приоритет другого шага и сохранение foreground busy после background callback;
- смену ориентации/инструмента, поздний успех после правки, замены и закрытия документа;
- отказ обычной валидации для испорченного прогретого результата;
- отмену и join при shutdown.

Реальная CAD/GUI-проверка — `large_route_workflow_tests --audit-prefetch`: собственный профиль 32 гиба, Linux/X11/GPU, Debug, 100%, обычный VSync. Первый шаг остался холодным; следующие были подготовлены заранее. Пример одного последовательного запуска:

| Переход | До предподготовки, мс | С готовым кэшем, мс |
| --- | ---: | ---: |
| К шагу 2 | 533 | 15,74 |
| К шагу 3 | 541 | 16,07 |

До — сохранённый диагностический запуск D157 на той же fixture, не гарантированный универсальный benchmark. Подготовка следующего шага занимала 538–539 мс в фоне; сам worker при последующем переходе — 0,17–0,20 мс. Это перенос вычислений на время текущего воспроизведения, не ускорение CAD в десятки раз.

После очистки CAD-кэша дополнительно запущено настоящее воспроизведение 1 → 2 → 3. При 1× и 10× текущая анимация продолжалась, соответствующая подготовка при автопереходе не отменялась, пауза на шаге 3 прекратила дальнейшую спекуляцию. Поиск порядка не запускался. `manual_route_workflow_tests` с настоящим GPU сохранил D127, остановку на первой коллизии при 10×, локальные полосы, A/B, смену инструмента/шагов и устаревшие ответы.

Логи — ignored `out/prefetch-{playback,fast,manual}-native.log`, финальные `out/prefetch-delivery-native.log` и `out/prefetch-cache-stop-tests.log`; снимок столкновения — `out/prefetch-manual.png-collision-iso.png`. Windows/GPU, удалённый CI и HiDPI не запускались. Абсолютная RAM/VRAM и новая физическая модель не измерялись/не вводились.

```bash
cmake --build --preset dev --target draft_prefetch_tests large_route_workflow_tests
ctest --preset dev -R '^application.(draft-prefetch|import-controller)$' --output-on-failure
QT_QPA_PLATFORM=xcb QT_SCALE_FACTOR=1 \
  build/dev/bin/large_route_workflow_tests --audit-prefetch
```

`--audit-prefetch-fast` проверяет те же переходы при 10×; эти расширенные native-аудиты не добавлены в обязательный CI. Новый быстрый CTest проверяет жизненный цикл без CAD/GPU.

`--audit-manual-prefetch` проверяет последовательные ручные переходы на той же детали с 32 гибами. После паузы подготовка идёт без смены отображаемого шага и без блокировки управления. Следующий шаг использует готовый CAD-кэш. Прыжок и возврат назад не запускают предподготовку. На Linux/X11 Release при 100% переход к шагу 3 с уже подготовленной общей геометрией занял 461–481 мс, с готовым результатом шага 12–13 мс. Расчёт должен завершиться до клика, чтобы получить эту задержку. Логи находятся в `out/draft-transition-study/retained-native-prefetch*.log`.

Повторный нативный прогон 2026-11-10 на том же профиле с 32 гибами и текущим вьюпортом. Холодные переходы к шагам 2 и 3 заняли 502 и 518 мс, из них 489 и 503 мс в worker. С готовой фоновой подготовкой переходы заняли 26 и 12 мс, из них менее 0,3 мс в worker. Вызов выбора шага занял 1,9–3,5 мс. Проигрывание на 10× дошло до шага 3 и штатно остановилось по паузе. Логи находятся в `out/export-transition-audit/{cold,ready}.log`.

### Пауза при автопереходе

`large_route_workflow_tests --audit-playback-gap` измеряет время от показа последнего кадра до публикации следующего шага в UI. Оно включает штатный интервал таймера и обработку событий. На профиле с 32 гибами под Linux/X11 в Debug получено 57–62 мс при 1×, 126–145 мс при 3× и 211–217 мс при 10× без форы. Диагностический флаг `--audit-playback-head-start` даёт первому фоновому расчёту 500 мс перед Play. При 10× первый переход занял 16–18 мс, второй 206–252 мс. Ранний запуск остался диагностическим. Логи находятся в `out/playback-gap`.

### Разбивка холодного расчёта

На том же профиле с 32 гибами и прогретой общей геометрией шаги 1–3 занимали 469–503 мс в worker. В отдельном прогоне с разбивкой проверки инструмента на стадии построение ограничивающих коробок заняло 15–16 мс, а цикл проверки пар после построения коробок — 382–384 мс. В этот цикл входят отсев по коробкам, точные CAD-пересечения, проверка результата и вычисление объёма. Положения и тела листа заняли 57–58 мс, сетка и сборка отображения — 25 мс. Станок, подсветка и завершение проверки упоров суммарно заняли менее 1 мс на этой установке. Это замер конкретной оснастки и маршрута, а не универсальная оценка сложности. При повторном выборе готового шага worker занимал 0,15–0,31 мс. Временные таймеры сняты, логи сохранены в `out/draft-stage-audit`.

### Повторные пары и ориентированные коробки

Диагностический прогон сравнивал идентичность тел, ориентацию, допуск и все 12 коэффициентов относительного преобразования без округления. Считались повторы ранее подтверждённого нулевого объёма внутри одного гиба. На профиле из 32 гибов проверка обычных коробок оставила 126 из 2751 пар на гиб. В ручном сценарии осталось 139 из 399. Среди оставшихся пар не было попаданий в пробный кэш и дополнительного отсева по ориентированным коробкам OCCT. Диагностика выполняла прежние точные пересечения для всех кандидатов. Логи находятся в `out/draft-pair-audit`.

### Покрытие инструмента несколькими коробками

2026-11-10, локальный эксперимент на Linux/X11 при 100%. Для каждого инструмента пробовали восемь перекрывающихся слоёв по каждой оси отдельно. Границы каждого слоя получали через точное пересечение тела с плитой и расширяли с учётом допусков. При предупреждении или ошибке разрезания использовали общую коробку. Покрытие строилось один раз на шаг, коробки пуансона перемещались вместе с ним. После обычного отсева проверяли пересечение коробки тела детали со всеми коробками покрытия. Прежний точный OCCT-расчёт выполнялся в любом случае и определял результат. Станок, упоры и проверка пары «матрица — пуансон» в эксперимент не входили.

- Профиль с 32 гибами, пять расчётов ненулевого шага. Разбиение матрицы по глубине X дополнительно отсеивало 21 из 63 пар «деталь — матрица» на шаг. Эти пересечения занимали 44–45 мс, построение покрытия 51–54 мс. Для пуансона и остальных осей дополнительного отсева не было.
- Ручной сценарий с коллизией, 22 расчёта ненулевого шага. Покрытие по X отсеяло 314 из 1386 пар с матрицей и 94 из 1386 пар с пуансоном. В двух расчётах матрицы отсеянные пересечения заняли 250–266 мс при цене покрытия 51–53 мс. Выигрыш зависит от установки. По высоте Y полезный отсев встречался только для пуансона, по длине Z его не было.
- Во всех предложенных к отсеву проверках точный OCCT вернул нулевой объём. Это наблюдение по двум наборам оснастки и положений. Оба нативных сценария прошли.

Покрытие в симуляцию не включено. Перестроение на каждом шаге не окупается на профиле с 32 гибами. Отдельная гипотеза для следующего эксперимента — готовить покрытие по X только для матрицы и переиспользовать его для неизменной сборки. Замеры показывают цену потенциально исключаемых пересечений, фактическая задержка после их исключения не измерялась. Временный код снят. Скрипт диагностики и логи находятся в ignored `out/draft-cover-audit/`.

### Повторное использование покрытия матрицы

2026-11-11, локальный эксперимент. В CAD-потоке хранилось одно покрытие матрицы из восьми слоёв по X. Ключ сравнивал полные параметры инструмента, назначение и допуск без округления. Такой ключ консервативен и может давать промах даже при неизменной матрице, например при смене пуансона. При ошибке или предупреждении разрезания использовалась общая коробка. Проверяли три режима одного бинарника: исходный, сверка с точным OCCT и фактический отсев.

Профиль с 32 гибами, Linux/X11, Debug, масштаб 100%. По два прогона исходного режима и режима отсева, по три перехода к ещё не рассчитанному шагу в каждом. Покрытие уже готовилось на шаге 0 (около 51 мс), последующие шаги попадали в кэш и пропускали 21 из 63 проверок «деталь — матрица» после общей коробки.

| Медиана шести переходов | Исходный режим | Фактический отсев |
| --- | ---: | ---: |
| Расчёт в worker, мс | 492 | 437 |
| От выбора шага до публикации, мс | 506 | 451 |

Повторное открытие уже готового шага обслуживал существующий кэш кадров, эти переходы исключены из таблицы. Результат относится к ручному просмотру, автопоиск и чертежи здесь не измерялись.

Сверка на обоих сценариях подтвердила нулевой объём для 430 предложенных к отсеву пар, включая шаг 0. В режиме фактического отсева ручной сценарий сохранил остановку на столкновении и подсветку. Оба нативных теста прошли. Экспериментальный C++ снят, dev-app пересобран. Скрипт и логи лежат в ignored `out/cached-die-cover/`. Перед подключением фильтра нужно подтвердить полноту покрытия для поддерживаемых форм матрицы и привязать его к существующему ключу геометрии матрицы.
