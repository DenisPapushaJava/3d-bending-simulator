# Разработка и проверки

Дата: 2026-10-17. Создан технический каркас, а не работающий симулятор гибки.

## Начальный набор

- C++20, CMake 3.24+, Ninja.
- Qt Widgets 6.4+; в Ubuntu 24.04 используется системная 6.4.2, в Windows CI — 6.8.3.
- OCCT 7.6–7.9: Ubuntu 24.04 — 7.6.3, Windows — 7.9.3#1 из зафиксированного vcpkg.
- Для STEP нужен Data Exchange: `libocct-data-exchange-dev` на Linux; Windows использует уже собираемый OCCT из vcpkg. CMake выбирает `TKSTEP` (7.6/7.7) либо `TKDESTEP` (7.8/7.9). Экспортированные SDK-цели также требуют загрузить Visualization/ApplicationFramework; CAD-код не использует Qt.
- Windows x64 / MSVC 2022; Linux x64 / GCC 13, базовый дистрибутив Ubuntu 24.04, также Mint 22.x.
- Python 3.10+ нужен только инструментам проверки версии и упаковки; в приложение не входит.

Здесь указан набор стартового каркаса. Разные версии зависимостей на двух ОС проверяют совместимость API; точное воспроизведение системных Ubuntu-пакетов зависит от обновлений репозитория. OCCT 8 намеренно не принимается до отдельной проверки миграции.

## Linux

На Ubuntu 24.04 / Mint 22.x:

```bash
sudo bash scripts/install-linux-deps.sh
cmake --preset dev
cmake --build --preset dev --parallel 2
ctest --preset dev
./build/dev/bin/3d-bending-simulator
```

Без изменения системных пакетов можно использовать Docker:

```bash
docker build -f tools/Dockerfile -t 3d-bending-dev:ubuntu24.04 .
docker run --rm --init --user "$(id -u):$(id -g)" -v "$PWD:/workspace" \
  3d-bending-dev:ubuntu24.04 bash -c \
  'cmake --preset release && cmake --build --preset release --parallel 2 && ctest --preset release'
```

Контейнер проверяет сборку, окно с Qt offscreen и рендеринг через Xvfb/Mesa при наличии этих инструментов. Это software OpenGL, отдельный от проверки на реальном GPU. Использовать `--init`, чтобы Xvfb-run корректно получал сигнал готовности X-сервера и не становился PID 1 при запуске отдельной графической команды.

Проверка до M1.1, 2026-10-17: GCC 13.3 / Qt 6.4.2 / OCCT 7.6.3, сборка Release, три CTest и запуск из распакованного .deb успешны. До добавления просмотрщика runtime-зависимости .deb включали Qt; теперь он также использует OCCT visualization/modeling. Упаковка пересчитывает зависимости при добавлении CAD-функций.

Дополнительно .deb установлен с `--no-install-recommends` в чистый контейнер Ubuntu 24.04 без SDK/компилятора; проверка запуска успешна. `qt6-qpa-plugins` указан явно, поскольку такие плагины загружаются динамически и не попадают в список обычных библиотечных зависимостей.

## VS Code на Linux

Открыть корневую папку проекта. Нужны расширения Microsoft C/C++ и CMake Tools; рекомендации включены в `.vscode/extensions.json`. Зависимости устанавливаются Linux-скриптом выше; для отладки дополнительно нужен `gdb` (`sudo apt-get install gdb`).

Готовые команды не требуют предварительного выбора пресета в палитре:

- **F5** → «Симулятор — Linux (GDB)»: настроить `dev`, собрать и запустить приложение под отладчиком. Точки останова работают в C++-исходниках.
- **Ctrl+F5**: собрать и запустить без отладки.
- **Ctrl+Shift+B**: настроить и собрать `dev`.
- «Терминал → Запустить задачу» → «Linux: проверить dev»: собрать и запустить CTest.

Задачи используют `cmake --preset dev` из корня проекта и корректно передают пути с пробелами. IntelliSense читает `build/dev/compile_commands.json`, созданный при настройке. Эти задачи и GDB-конфигурация предназначены для Linux; Windows-среда описана ниже.

В русской локализации палитра CMake содержит названия «Выбор предустановки конфигурации», «Настроить», «Сборка» и «Отладить». Для ручной настройки выбрать пресет `dev` и цель `bending_simulator`. Если список ещё не обновился после установки расширений, выполнить «Разработчик: Перезагрузить окно».

Проверка 2026-10-17 на локальном Linux Mint: конфигурация `dev`, сборка и три CTest успешны; GDB остановился в `src/app/main.cpp` и завершил `--smoke-test` через обычный графический сеанс.

## Windows

Установить Visual Studio 2022 с Desktop development with C++, CMake/Ninja, Python и Qt 6.8.3 MSVC 2022 x64. Использовать **Developer PowerShell for VS 2022**, чтобы `cl` был доступен. `Qt6_DIR` или `CMAKE_PREFIX_PATH` должен указывать на выбранную Qt.

```powershell
git clone https://github.com/microsoft/vcpkg .deps/vcpkg
git -C .deps/vcpkg checkout 256310531c1e57ee83f8ac01f7bea7c1e56630f5
./.deps/vcpkg/bootstrap-vcpkg.bat -disableMetrics
cmake --preset release "-DCMAKE_TOOLCHAIN_FILE=$pwd/.deps/vcpkg/scripts/buildsystems/vcpkg.cmake" -DVCPKG_TARGET_TRIPLET=x64-windows-release "-DVCPKG_OVERLAY_TRIPLETS=$pwd/cmake/triplets" "-DVCPKG_INSTALLED_DIR=$pwd/vcpkg_installed"
cmake --build --preset release --parallel 2
ctest --preset release
./build/release/bin/3d-bending-simulator.exe
```

Triplet собирает общие DLL и только Release для зависимостей. Он не требует компилировать Qt из исходников: Qt поставляется отдельно официальной сборкой. Для локальной Debug-конфигурации OCCT нужно отдельно согласовать triplet/CRT, не использовать Release-only triplet как обещание поддержки всех Debug-комбинаций.

## Структура

У каждого модуля свой `CMakeLists.txt`; публичный API расположен в `src/<module>/include/bending/<module>/`. Включать заголовки как `bending/core/BendSequence.h`. Каталог `src` целиком не публикуется. Создание зависимостей выполняется в `src/app/main.cpp`; обычные виджеты не вызывают CAD SDK.

| Каталог / цель | Ответственность |
| --- | --- |
| `src/core`, `bending_core` | Независимый C++: стабильные ID гибов и перестановка с определением первого затронутого шага |
| `src/simulation`, `bending_simulation` | Чистая кинематика одного равномерного сгиба: средняя поверхность, сечение и промежуточные состояния; зависит только от core |
| `src/application`, `bending_application` | Стандартные типы документа/ошибки, порт импорта и машина состояния с ревизиями; без SDK/Qt |
| `src/cad`, `bending_cad` | Реализация порта импорта, PIMPL, единицы/метаданные/грани/триангуляция; Bending::CadOcct выделяет нативный мост viewer |
| `src/viewer`, `bending_viewer` | Нативный QWidget/OCCT с PIMPL: подготовленный CAD-документ, камера, выбор грани текущей ревизии, framebuffer и диагностика |
| `src/ui`, `bending_ui` | Окно, свойства/ошибки, диалог STEP и ImportController с одним QThread; порт импорта передаётся из app |
| `src/app`, `bending_simulator` | Настройки Qt, создание/соединение компонентов, запуск, диагностический `--smoke-test` |
| `tests` | Перестановка/ошибки без изменения данных, связь OCCT, создание окна, правила версий |
| `scripts`, `cmake` | Сборка, упаковка и согласованность версий |

Пустые модули заранее не создаются: simulation добавлен с работающим кинематическим сценарием M3.1; planning появится с реальным потребителем. Адаптер хранения `project` добавлен с рабочим сценарием M2. Они появятся вместе со сценариями из [первого плана](implementation-plan.md), сохраняя границы из архитектуры. UI не показывает искусственных успешных проверок и не содержит демонстрационных данных Figma как результатов расчёта.

Предметная часть отдельно, без Qt/OCCT:

```bash
cmake --preset core
cmake --build --preset core --parallel 2
ctest --preset core
```

Для CAD-адаптера без GUI: `cmake -S . -B build/cad-only -G Ninja -DBENDING_BUILD_APP=OFF`; затем обычные `cmake --build build/cad-only` и `ctest --test-dir build/cad-only --output-on-failure`. `BENDING_BUILD_CAD=OFF` допустим только вместе с `BENDING_BUILD_APP=OFF`.

## Соглашения C++ и проверки

- Стандарт C++20; пространства имён `bending::<module>`, классы/файлы `PascalCase`, методы `lowerCamelCase`, форматирование clang-format 18. Новая зависимость подключается на конкретную CMake-цель.
- Публичные заголовки содержат необходимые объявления и собственные include. Реализация и SDK-детали скрыты; `PIMPL` и виртуальный интерфейс применяются при реальной необходимости границы, а не для каждого класса.
- Владение через значения/RAII, сервисы обычно через `unique_ptr` и ссылки, виджеты через Qt-parent. Borrowed-ссылки и `string_view` имеют явно ограниченное время жизни; совместное владение требует причины.
- Проверять пользовательские численные параметры на конечность, единицы и допустимый диапазон до изменения документа. Ожидаемые ошибки адаптера возвращать как данные сценария; исключения SDK не выпускать в Qt event loop. Текущие исключения инвариантов core не скрывать общим `catch (...)`.
- Правила длины/угла, ревизий, отмены, потоков и актуальности результатов — в [архитектуре](architecture.md); они должны соблюдаться в каждом новом сценарии.
- `unit` проверяет core без SDK; `integration` — реальный CAD-адаптер и запуск окна. `ctest --preset dev -L unit` и `-L integration` позволяют выбрать группу. Геометрические тесты содержат известный результат и явный допуск; новые сценарии проверяют также отказ без потери прежнего состояния.

## Ветки и pull request

Согласовано с пользователем 2026-10-17, D016: один PR на законченный функциональный блок либо существенное самостоятельное исправление. Размер определяется связностью и проверяемым результатом, а не числом строк. Шаги реализации, промежуточные исправления, тесты, документация и связанная упаковка могут состоять из нескольких коммитов одной ветки. Отдельный PR ради каждого мелкого изменения не требуется.

Например, ближайшая фича «Открытие STEP и просмотр детали» объединяет M1.3 и M1.4 со связанными проверками и документацией M1.5. Другие возможные блоки — сохранение/открытие проекта или редактирование ручного маршрута. Несвязанные фичи не объединять только ради объёма; внутренние ID задач не задают границы PR.

Порядок работы:

1. Начать ветку `feat/<результат>` или `fix/<проблема>` от актуального `main`; постоянная `develop` не нужна.
2. Работать в ней до проверяемого результата, делать промежуточные коммиты и push. Мелкие связанные правки остаются в этой же ветке; согласования правил можно включать в текущую/следующую подходящую ветку.
3. Оформить один PR с описанием результата, проверок и ограничений; при необходимости ранней обратной связи использовать draft этого же PR. Результат просматривается до слияния, код проходит предусмотренные CI-проверки Windows/Linux; для документации применяются облегчённые проверки.
4. Слить готовый PR через `Squash and merge`: один итоговый коммит фичи в `main`.
5. После подтверждённого слияния удалить ветку на GitHub и локально, предварительно убедившись в отсутствии несохранённых и уникальных нужных изменений. Следующую фичу начинать новой веткой от обновлённого `main`.

Релизы выпускаются тегами на проверенном коммите `main`, по [releases.md](releases.md). Это принятое соглашение работы. На момент его записи защита `main` и автоматическое удаление веток на GitHub ещё не включены; настройку обязательных проверок нужно согласовать с docs-only CI, чтобы PR документации не оставался в ожидании отсутствующей проверки.

## CI

Один workflow `.github/workflows/ci.yml`:

1. Проверка VERSION, записи в CHANGELOG.md и совпадения с тегом, тесты правил версии и clang-format. Отдельная сборка `core` с запрещённым поиском Qt/OCCT контролирует независимость предметной части.
2. Две сборки: Ubuntu 24.04 и Windows 2022. Сборка Release, CTest, проверка старта окна.
3. Linux .deb с автоматически определёнными зависимостями; Windows ZIP с DLL, Qt-плагинами, лицензиями и исходниками зависимостей. Проверяется запуск из собранного комплекта.
4. Артефакты для main и тегов хранятся 7 дней; по тегу создаётся черновик релиза.

Push проверяется только в main, остальные ветки — через PR, чтобы не дублировать один и тот же запуск. Правки только Markdown/docs/design не запускают тяжёлые сборки. Старые запуски веток отменяются; запуски тегов не отменяются. Разрешение записи есть только у задачи черновика релиза. Actions закреплены SHA, их обновления группирует Dependabot раз в месяц. OCCT имеет отдельный двоичный кэш; первый Windows-запуск будет заметно дольше следующих.

Нет develop-ветки, обязательного числа ревью, автоматического изменения версии или сложного release-бота. Ветки и PR объединяют законченные функциональные блоки по D016, со всеми связанными мелкими изменениями. Интерактивные графические проверки обеих ОС, установщик, подпись Windows и универсальный AppImage — последующие задачи.

Фактический первый прогон 2026-10-17: установка/сборка полного OCCT SDK через vcpkg на Windows заняла около 45 минут. После неё сборка самого каркаса заняла 9 секунд, CTest — около 2 секунд. Это стоимость холодной зависимости; кэш двоичных пакетов сохраняется отдельным шагом до упаковки. Ключ включает manifest/triplet и версию MSVC. При изменении ключа восстанавливается предыдущий кэш, а vcpkg проверяет ABI каждого пакета перед использованием. VERSION не дублируется в manifest, поэтому смена номера выпуска не меняет ключ SDK.

На PR выполняются сборка и тесты обеих ОС, а также Linux-упаковка. Windows-упаковка с полным комплектом соответствующих исходников выполняется для main и тегов; артефакты PR не публикуются.

Это проверка каркаса без реального CAD-просмотра и моделирования; интерактивная проверка на целевом Windows-ПК ещё предстоит. Выпуск по тегу пока не запускался, релиз не опубликован.

## Просмотрщик M1.1 и графические проверки

Нативное окно Qt/OCCT работает с Windows или Linux/X11; Wayland пока через XWayland и `QT_QPA_PLATFORM=xcb`. OCCT создаёт контекст; Qt OpenGLWidgets не используется. Драйвер OpenGL — системный. В Windows Shaders копируются в `share/opencascade/resources/Shaders`, в Linux используются системные ресурсы OCCT. `libfontconfig-dev` нужен для корректной линковки импортированного TKService в Ubuntu; в контейнере он указан явно.

Управление: ПКМ — вращение, СКМ — перенос, колесо — масштаб, ЛКМ — выбор/очистка выбора грани, F — вписывание. Проекции задаются на панели «Камера». Сцена содержит только тестовый параллелепипед 100 × 60 × 20 мм; импорт и технологическая модель ещё отсутствуют.

```bash
# Окно/диагностика на offscreen-платформе, без доказательства GPU-работы:
ctest --preset dev -L integration
# Настоящий контекст и framebuffer в графическом сеансе:
./build/dev/bin/3d-bending-simulator --graphics-smoke-test
./build/dev/bin/viewer_tests
QT_SCALE_FACTOR=2 ./build/dev/bin/viewer_tests
# Необязательный снимок только сцены, не всего рабочего стола:
BENDING_VIEWER_SNAPSHOT="$PWD/out/viewer-demo.png" ./build/dev/bin/viewer_tests
```

`viewer_tests` проверяет непустое изображение геометрии, выбор реальной грани, проекции и изменение кадра при вращении/переносе/масштабировании, физический размер framebuffer, resize, hide/show, minimize/restore и новое создание ресурсов. Это сценарии реального OCCT, а не макеты результатов. Публичный метод `captureImage()` читает OCCT framebuffer: обычный QWidget::grab не предназначен для захвата такого нативного дочернего окна.

При наличии `xvfb-run` CMake регистрирует `viewer.render` и `viewer.render.hidpi` с меткой `graphics`. Они запускают отдельный X11-сервер с Mesa software OpenGL при DPR 1/2. Скрипт установки/Docker включает Xvfb/xauth/Mesa. В Windows CI проверяются сборка, недоступный offscreen backend и упаковка; для проверки OpenGL-драйвера нужен отдельный интерактивный запуск.

M1.1: локально прошли сценарии на NVIDIA GTX 1650 / OpenGL 4.6 при Qt 6.4.2 и OCCT 7.6.3. Локальный оффскрин-набор содержит 5 тестов; Linux с Xvfb — 7. Переход между настоящими мониторами/DPI и интерактивный Windows/GPU остаются открытыми. Отрицательная проверка `app.graphics-unavailable` гарантирует, что графическая диагностика не сообщает успех без поддерживаемого backend.
