# Ранжирование и повторное использование расчётов — D081

## Осевой отсев при подборе оснастки

Подбор проверяет покрытие по длине для всех гибов, назначенных варианту. Если фиксированная сборка доказанно коротка, поиск переходит к следующему варианту. Такой отказ возникает до расчёта переходов и сохраняет их бюджет. Если запрос разрешает пересобрать секции для данного гиба или допускает подтверждаемую опору на прямой части подрезанного торца, вариант проходит к обычной проверке. Ошибки самого запроса сохраняют приоритет над диагностикой длины.

Контрольный сценарий использует две DXF-пары и бюджет в одну проверку. Первая сборка слишком короткая, вторая даёт проверенный маршрут за одну проверку. Если оставить только первую сборку, расчёт возвращает исходную диагностику длины при нуле проверок.

Отдельные эксперименты для дальнейшего сравнения:

1. Измерить отсев фиксированных сборок и проверку достижимых длин секций. Для исключения требуется доказать, что допустимой сборки или позиции нет во всей разрешённой области.
2. Сравнить очередность поиска по числу оставшихся вариантов установки. Близость полок и предварительная оценка упоров служат признаками для ранжирования. Отказ конкретного положения относится к его состоянию детали.
3. После первого полного маршрута отдельно измерить улучшение по переналадкам и переворотам. Сравнивать время до первого маршрута, число точных проверок и долю найденных маршрутов при равном бюджете.

2026-10-29. По прямому поручению пользователя применить предложенные эвристики/повторное использование и проверить регрессии. Основа — [исследование производительности](bend-route-performance.md), принципы эвристического поиска из публикации CMU и пример организации состояний BendSeq. Реализован собственный C++-код, внешних зависимостей/заимствованных исходников нет. D051: локально.

## Что изменилось

Обратный DFS и общий `buildBendOperation` сохранены. Для автоматического поиска кандидаты получают мягкий приоритет:

1. Точный переход уже имеет успешную геометрическую проверку.
2. Переход ещё не проверен.
3. Обе его стороны уже получили устойчивый отрицательный результат в этом же состоянии/режиме.

Внутри группы раньше пробуются зоны с меньшим числом оставшихся согнутых соседей на смежных стенках. Это дешёвая топологическая оценка доступности, не измерение зазора до инструмента. При равенстве сохраняется приоритет исходного порядка. Для сторон подачи используется такой же приоритет «проверено / неизвестно / отрицательный результат», при равенстве — прежний A/B.

Эвристика **не исключает** ни гиб, ни сторону. Каждый новый принятый переход по-прежнему проходит полный общий цикл и две разности с каноническим предшественником. Автоматический результат может иметь другой допустимый порядок. Ручной запрос строго сохраняет порядок операций; выбор одной из двух разрешённых сторон подачи остаётся частью проверки, как раньше. Оптимум по времени/числу перестановок не обещается. При ограниченном бюджете очередность может влиять на найденный результат; отсутствие пути не обобщается на невозможность изготовления.

## Канонические состояния и два слоя переходов — D081/D111

Владельцем является конкретный `cad::SingleBendPreviewBuilder`, не глобальный singleton. Он хранит рабочий набор только последнего документа. Ключ набора — **идентичность неизменного DocumentPtr и точное значение/происхождение ручной толщины**. Совпадения пути/имени файла недостаточно. Новый импорт того же STEP получает другой документ и новый набор. Изменение файла на диске не меняет уже захваченный документ.

Первый уровень хранит проверенную геометрическую развёртку K=0,5 и канонические промежуточные состояния по маске. Толщина/допуски, распознанные связи и режим заполненной копии принадлежат захваченному документу/набору. Материал/K технологической развёртки не является входом этой кинематики. SDK-данные остаются внутри CAD.

Данные перехода разделены: до **max(8, N) успешных полных циклов** с кадрами (N — число гибов, максимум 32; D114) и до **512 компактных ответов** (успешная подсказка либо устойчивый отказ без диагностической геометрии). Отказы больше не вытесняют успешные кадры. Положительная подсказка без удержанного цикла влияет только на рейтинг: для выдачи результата цикл строится и проверяется заново. Это не готовый маршрут с чужой ревизией. Полный вход перехода содержит:

- маску состояния после операции;
- исходный индекс/ID зоны и целевые угол/радиус;
- сторону подачи;
- режим с инструментом/без;
- полные численные параметры инструмента и снимок назначения: оба пресета, фактические контуры/активный ручей, составы, позиции/зазоры секций и прочие поля ToolAssignment;
- разрешение условной неполной торцевой опоры D077.

Контуры сравниваются по данным, а не только артикулу или заявленному SHA. Поэтому профиль с теми же рабочими размерами, но другим корпусом не наследует старый результат. В режиме без инструмента неиспользуемые назначения не входят в ключ. Бюджет, очередность и стратегия поиска не меняют геометрию отдельного перехода и в этот ключ не входят.

Успех сохраняется только после полного `buildBendOperation` и независимой проверки начала по двум разностям. Для отрицательных результатов задан явный список устойчивых геометрических/контактных ограничений, включая столкновение, неподтверждённую опору/отвод и неподдержанный профиль инструмента. «Не подтверждено» сохраняет свой смысл, не превращается в доказанную невозможность. `Failed`, `Cancelled`, `UnsupportedGeometry`, ошибки Boolean и результат `NoRoute/SearchLimit` целиком не кэшируются. Тупики по маскам остаются **внутри одного запроса**, поскольку ручной порядок задаёт другие ограничения.

Полностью завершённые переходы из запроса, достигшего SearchLimit, доступны следующей команде «Расширить поиск». Обход начинается заново и может использовать эти доказательства; это не продолжение старого стека DFS. Бюджет кандидатов включает попадания в кэш, поэтому ранее заданный предел не обходится.

## Индексы, ключи и отложенное построение — D111

Оба слоя переходов используют `std::unordered_map` для поиска и стабильные узлы `std::list` для LRU: ожидаемо O(1) на обращение, с проверкой равенства ключа при коллизии хеша. Оценка кандидата читает ответ без изменения LRU; фактическое использование поднимает запись. Это RAM-индекс, не формат файла и не обещание худшей сложности O(1).

Полный неизменный вход интернируется **при подготовке каждой операции запроса**, с точным сравнением значений в реестре доступных снимков; эта подготовка не выполняется для каждой поисковой попытки. Реестр интернирования просматривается линейно, хеш-индекс применяется к многочисленным ключам переходов. Записи по разным маскам разделяют этот снимок; малый ключ содержит маску, ссылку на снимок и физическую сторону детали. Контуры больше не копируются/не сравниваются при каждом сравнении сортировки и поиске перехода. Совпадение имени, исходного DXF SHA или хеша не заменяет сравнение чисел/рёбер. Снимки держатся `shared_ptr<const …>`, реестр интернирования — `weak_ptr`; вытесненные входы освобождаются и при следующем обращении удаляются из реестра. Адреса используются только внутри текущего процесса, никогда как дисковые идентификаторы.

В компактном отказе сохраняются код, текст, индекс кадра и данные опоры; диагностический preview не удерживается. Его единственный потребитель здесь — поисковый отчёт `BendRouteError`, который не содержит кадров. Одиночный/ручной просмотр продолжает получать полноценную локальную диагностику своим общим checker и собственным кэшем. `reusedTransitions` включает все повторно использованные ответы, `reusedRejections` выделяет обращения к компактным отказам. Пустая запись означает успешный рейтинг, а не пустой успешный цикл.

Канонический предшественник теперь строится после успешного `buildBendOperation`: отвергнутой попытке он не нужен. У принятого перехода остаются обе независимые разности всей формы и все прежние кадры/проверки. Успех не публикуется до их завершения. Не добавлено межсостоянийное отсечение вида «этот гиб не прошёл здесь — он не пройдёт нигде». Бюджет включает попадания в кэш; SearchLimit/отмена/ошибка SDK не становятся отрицательным доказательством.

## Владение и актуальность

Геометрические состояния ограничены **32 записями LRU**, успешные циклы — **8**, компактные ответы — **512**. Эти пределы ограничивают число объектов, а не гарантируют фиксированный объём RAM: большие модели/61 кадр могут занимать много памяти. Активные состояния/кадры держатся shared_ptr, поэтому вытеснение записи не удаляет данные из выполняющейся операции или открытого результата.

Смена исходника/толщины заменяет набор. Открытие/закрытие документа, отмена и завершение приложения вызывают `discardRouteCache`; замена адаптера также очищает прежний. Очистка меняет общую ссылку под короткой блокировкой, не ожидая завершения активного CAD-вызова. Выполняющаяся задача сохраняет локальное владение до выхода. Доступ к содержимому набора защищён отдельно. Отмена проверяется до чтения/публикации результата и сохранения перехода; отменённый запрос отзывает сохранённый набор.

Изменение параметров по-прежнему немедленно снимает **видимый** готовый результат. Повторное использование возможно только после новой команды проверки с совпадающими входами. Кэш не обходит ID/DocumentRevision/EditRevision и отмену в ImportController. На GUI передаётся новый BendRoute с актуальным источником и порядком, даже если отдельные неизменные preview разделяются с прошлой проверкой. Переключение кадров/цветов/камеры не меняет геометрию.

Переходы детали остаются в RAM; постоянный кэш оснастки D091 независим от них. Форматы `.bend` и каталога не расширяются. После открытия проекта по-прежнему требуется проверка. Флаги `rankCandidates/reuseCalculations` доступны в прикладном запросе для диагностического сравнения; GUI использует оба улучшения без новых настроек.

Это корректно только для текущих **независимых установок открытого дерева**. При добавлении переноса, держателей/станка, позиций станций, базирования или физики пути нужно расширить состояние/ключ и перепроверить эквивалентность; одной маски для новых условий недостаточно.

## Проверка

В `route_optimization_tests` сравниваются отключённые оптимизации и текущий поиск. Проверяются одинаковая достижимость/класс отказа, полнота зон/префикса, исходный источник, число кадров, объём/валидность материала, параметры каждого инструмента и сертификат отвода. Отдельный ветвящийся fixture действительно меняет порядок проб, но сохраняет полный допустимый маршрут.

Проверяются строгий ручной порядок, тёплый запрос без новых построений, смена режима, изменение зазора только одной операции, другой корпус при тех же размерах, возврат к прежнему профилю, отрицательный результат, вытеснение старых переходов, другой импорт, происхождение толщины, отмена и явная очистка. В GUI проверены повторная выдача тех же неизменных preview, возврат ползунка к началу, отсутствие автоматического расчёта и очистка при закрытии. D077 дополнен строгим запросом **к тому же адаптеру**, уже содержащему условный маршрут: разрешение неполной опоры не переносится в строгую проверку.

Сравнения времени — локальные последовательные native Release-прогоны, один вариант за другим. Замеряется вызов buildRoute после импорта; независимые дополнительные проверки результата в тесте и перерисовка GUI в замер не входят. Тёплый запрос должен иметь ноль новых переходов/состояний — это проверяется счётчиками, а не нестабильным порогом секунд. Частные модели используют явно условный инструмент V≈8t, а не подтверждённый склад/нагрузку станка. Численные результаты и прогоны — в [журнале исследования](research.md) и [разработке](development.md).

На простых деталях оба порядка часто проходят с первой попытки, поэтому эвристика не обязана ускорять первый расчёт. Единичные различия холодного времени не доказывают её выигрыш. Повторный расчёт ускоряется за счёт реального повторного использования проверенных переходов.

## Приоритет свободных краёв на деталях с вложенными полками

Для автоматического поиска с инструментом по разветвлённому графу полок вычисляется расстояние от каждой полки до ближайшей свободной полки. Гиб получает меньшую из глубин двух соединяемых полок. В обратном поиске при равном результате прежних проверок сначала пробуются более глубокие гибы. В прямом порядке это даёт приоритет отгибам у свободных краёв перед закрывающими их стенками. Признак вычисляется один раз по связям развёртки. Действующие пробы сторон подачи, общих сборок и геометрические проверки используются для каждого перехода.

В проверочном корпусе признак разделил восемь гибов на две группы. Покадровая проверка одной сборки подтвердила полезность такого начального порядка. Полный цикл корпуса пока ограничен построением геометрии отвода и выделением подрезанной зоны. [Протокол](manual-control-box-route-audit.md#независимая-проба-порядка-по-геометрии).

## Общая сборка с двумя сапожками и подрезанные зоны — D248

Если граф стенок разветвлён и соседние сформированные полки ограничивают осевой доступ с обоих концов хотя бы одной внутренней зоны, поиск сначала даёт короткий проход одной общей сборке с двумя настроенными сапожками из наличия. Уже установленная подходящая парная сборка используется первой. В обратном порядке сначала проверяются внутренние гибы, при равной глубине длинные имеют приоритет. Для положения детали сохраняется предпочтение основной частью к оператору. Первый проход пробует центр с обеих сторон подачи. Крайние осевые положения остаются в основном поиске. Предел первого прохода равен максимум удвоенному числу гибов и входит в общий лимит. Для уже подтверждённой части пути действует увеличенная доля времени пары в пределах общего бюджета. Прямые и другие сборки остаются кандидатами. Вывод о столкновении даёт штатная проверка точной геометрии.

В одиночной подрезанной зоне многотельный результат Common может взять точный сектор из исходного проверенного разбиения. Маршрут переносит этот сектор тем же жёстким преобразованием, которым строит текущее состояние, после однозначной привязки зоны. Проверки радиальной геометрии, разделения по реальным граням, обеих реконструкций, контактов, упоров и коллизий выполняются для текущего состояния. Две направленные разности используют одну подготовку пересечений OCCT. Каждая разность независимо строится, проверяется на валидность и измеряется с прежним допуском. Для отображаемой поверхности одинаковые координаты на стыках треугольных сеток используют уже доказанную принадлежность. Для исходной поверхности предел составляет 256 уникальных точек, для сетки промежуточного состояния из проверенного разбиения — 4096. Запросы расстояния переиспользуют подготовленные тела. Граница по расстоянию и проверка всех принадлежностей сохраняются.

В синтетической коробке с четырьмя гибами проверена общая сборка с сапожками при наличии только слишком длинной и слишком короткой прямых секций. Повторный запрос переиспользует проверенные переходы. Тест также проверяет запрет столкновения при слишком длинной сборке, отсутствие подмены фиксированной оснастки, отмену и равенство результата с отключённым кэшем.

## Приоритет прямой сборки на коробках без подгибов — D249

Соседние борта могут ограничивать осевой доступ и у простой коробки. Ранняя проба с двумя сапожками дополнительно требует, чтобы зона с ограничением с обоих концов соединяла две стенки ненулевой глубины. Для разветвлённой детали, у которой все гибы соединены со свободными полками, сначала проверяется исходная общая сборка. В этом проходе при прочих равных обратный поиск начинает с более длинных гибов. Сапожки и остальные установки доступны в резервном поиске.

Контрольная коробка 198 × 118 мм, максимальная длина гиба 178 мм. При наличии прямой секции 180 мм и двух сапожков прежний приоритет выбирал сапожки за четыре проверки. Новый проход оставляет прямую секцию и проходит четыре гиба за четыре проверки без подбора дополнительных сборок. В исходном наборе секция 250 мм сталкивается с деталью, а 50 мм не хватает по длине. В этом случае поиск по-прежнему находит сборку с двумя сапожками. На «Корпусе пульта++» диагностический запуск подтвердил, что ранний проход с двумя сапожками по-прежнему выбирается.

## Приоритет по уже согнутой соседней полке — эксперимент D250

Проверили узкий вариант двухуровневых признаков. При подготовке сохраняли отдельную 2D-оценку для направления «выполняем A после B» по полному контуру выбранного инструмента. В обратном поиске оценка влияла на порядок только пока B оставался в маске сформированных гибов. Существующие приоритеты по проверенным переходам, глубине полок и осевому доступу оставались старшими. Все кандидаты сохранялись и проходили те же точные проверки.

Сравнение выполнено на Linux Release с одинаковыми установками, ограничениями и отдельным холодным экземпляром расчёта для каждого варианта. Отобраны 52 установки Z-профилей, где оценки двух порядков различались: менялись высота ступени, длина короткой полки, радиусы и контур матрицы при одинаковом V. Оба алгоритма выполнили по 208 точных проверок и отклонили все 52 установки из-за столкновения. Медиана одного запуска — 442 и 439 мс соответственно. Этот замер не показывает выигрыша. На нескольких вариантах с нулевым 2D-риском для одного порядка точная проверка всё равно находила столкновение. Это исключает применение оценки в качестве допуска или доказанного отсева. Семь целевых тестов по выбору оснастки, коробкам, сапожкам и повторному поиску прошли с экспериментом. Локальный патч и протоколы находятся в `out/feature-route-ranking/`.

Эвристика в рабочий поиск не вошла. Ранжирование **пар инструмента** по полному контуру остаётся полезным: на проверочном Z-профиле первым проходит узкая матрица с тем же V, без точной пробы четырёхручьевой. Для следующего сравнения нужны случаи, где на одной оснастке проходит только часть порядков. Для коробок отдельно измерять число установок и цену одного точного перехода. Если путь уже найден за число проверок, близкое к числу гибов, ускорять следует подготовку и точную проверку перехода. Использовать жёсткий отсев по длине и положению только при доказанной несовместимости во всех разрешённых установках, с учётом настоящей формы оснастки, её концов и зазоров.
