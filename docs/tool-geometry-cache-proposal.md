# Сохраняемый кэш геометрии инструмента — D091

2026-10-30. Статус: **анализ кода и предложение, не реализация**. Пользователь предложил повторно использовать установку инструмента независимо от координат детали и отдельно потребовал сохранять вычисленный кэш между запусками программы и компьютера. Постоянное хранение — требование к будущему блоку; формат и границы ниже предлагаются для реализации. Действующий D090 ускоряет показ/повтор текущего запроса, но дискового кэша инструментов ещё нет.

## Что подтверждено кодом

- `DrawingTools.cpp::orientPunch` уже делает одну физическую ротацию Y на π через Z = Lматрицы/2 с помощью `shape.Moved(TopLoc_Location(...))`. Сам разворот не пересоздаёт контур. Сохранение двух дублирующих тел только ради этой операции не является обоснованным ускорением.
- `sectionPrism` заново строит wire/face/экструзию и проверяет валидность. `segmentToolBody` получает каждую секцию пересечением целого тела со slab через `BRepAlgoAPI_Common`. В ручном пути `RouteDraftGeometry` после построения оснастки запускает её триангуляцию. Это кандидаты на повторное использование; доля времени пока не измерена.
- `makeDrawingTools` сейчас совмещает построение тела с Y-положением носика и центрированием пуансона по длине матрицы. Полный цикл добавляет толщину/зазор, ручные кадры — текущую высоту носика. Эти мировые положения нельзя сохранять как единственную вечную установку артикула.
- `MachineAssembly` зависит от ревизии станка, высоты/посадки инструментов, длины установки и ориентации хвостовика. Неподвижные/подвижные группы уже отделены; проверка пересечений остаётся общей.
- D081/D082 кэшируют основание/состояния/переходы и несколько ручных результатов в памяти вокруг последнего `DocumentPtr`. Отдельного постоянного кэша тел инструмента между деталями/перезапусками нет.
- `ToolDrawing::sha256` — хэш исходных байтов DXF. Единицы, поворот/отражение, выбранный контур и активный ручей представлены численными данными отдельно. Один и тот же исходный SHA не идентифицирует фактически построенное тело.

Это чтение реализации, не замер ускорения или доказательство пригодности произвольного профиля.

## Предлагаемое разделение

| Слой | Что сохранять/повторять | Что остаётся переменным |
| --- | --- | --- |
| Профиль | Контур в мм, рабочая/монтажная базы, результат распознавания с версией алгоритма | Выбор другого контура, масштаба, базы или ручья |
| Секция | Точное локальное BRep-тело нужной длины, подготовленная сетка с её параметрами | Другая длина/реальная форма торца/качество сетки |
| Набор секций | Упорядоченные ссылки на секции и их локальные преобразования, зазоры | Порядок, пропуски, длины, типы торцов, зазоры |
| Монтаж | Положения относительно баз конкретного станка/держателя/адаптера для двух сторон | Ревизия станка, оснастка, станция/смещение и выбор рабочей стороны |
| Кадр гибки | Применить готовые локальные тела/преобразования | Высота пуансона, положение/форма детали и проверка столкновений |

Локальный базис: X поперёк V, Y вверх, Z вдоль гиба. Профиль нормализуется по явно заданной рабочей базе, длина секции — по её собственному центру; положения в установке задаются отдельно. Ротация на π вокруг Y преобразует **X и Z**: торцы/порядок асимметричного набора нельзя сохранять как обычное 2D-отражение. Два варианта могут ссылаться на одно точное тело и разные rigid transforms, без двух копий всей топологии/сетки. Состояние выбора ориентации сохраняется даже у симметричного тела.

Для поддержанных прямых экструзий отдельно проверить построение секции сразу на нужную длину вместо Common с длинным целым телом. При совпадении всей геометрии это может сократить холодное построение. Настоящий левый/правый рог, переменное сечение или отдельный 3D-торец требует собственной геометрии/ключа; надпись о роге в инвентарном шаблоне не доказывает такую форму.

Это внутреннее разделение не разрешает менять мировые тела/монтаж сохранённых DemoPressV1/V2. Эквивалентность старого и нового построения нужно проверить независимо; изменение самой геометрии модели станка требует нового идентификатора по D088.

## Диск и память

Первый реализуемый блок должен включать **оба** уровня: дисковые артефакты, переживающие обычный перезапуск ОС, и ограниченное переиспользование уже загруженных тел в памяти. При запросе сначала проверяется память, затем конкретная запись на диске, иначе тело строится и сохраняется. Загружать/генерировать весь каталог на старте не нужно.

Для Windows portable предлагается `data/cache/tool-geometry/` у корня комплекта, вне `runtime/<VERSION>` и временной `.updates`. Для обычной установки — постоянная локальная папка данных пользователя; не системный временный каталог и не каталог ОС для автоматически очищаемых временных кэшей. Нет срока годности по часам/датам; обычный запуск/перезагрузка ничего не очищают. Совместимое обновление приложения сохраняет данные. Ограничение занятого места/ручная очистка предлагаются отдельно после измерения размеров; не вводить скрытую очистку при каждом старте. Кэш — восстановимые производные данные, библиотека и снимки `.bend` остаются источниками.

Возможный состав записи: небольшой манифест, точное бинарное BRep с триангуляцией и контрольной суммой, параметры построения/версий. OCCT предоставляет `BinTools::Write/Read`, включая флаги записи треугольников и версию формата. Наличие API проверено в установленном OCCT 7.6.3; совместимость фактических артефактов Windows 7.9.x/Linux 7.6.x ещё не проверена. Первый формат лучше разделить по совместимой версии ядра/формата и сборки платформы. Новая версия алгоритма/несовместимый SDK получает новое пространство ключей; простое изменение VERSION приложения само по себе не требует уничтожать совместимый кэш. GPU-контекст/AIS-объекты на диск не сохранять.

Запись — во временный файл с последующим атомарным принятием готового артефакта; для нескольких файлов манифест публикуется последним. При прерывании записи остаётся прежняя запись либо отсутствие готовой записи. Контрольная сумма, формат/размер и валидность BRep проверяются при чтении один раз до публикации в память. Обычная перезагрузка сохраняет завершённую запись; внезапное обесточивание до завершения записи не должно выдавать частичный файл за готовый кэш. Безопасность постоянного хранения при аварии питания и гарантии записи конкретной ФС нельзя объявлять проверенными заранее.

SDK-чтение/построение/подготовка выполняются на прежнем CAD-worker, сцена получает только подготовленные immutable-тела. Триангуляцию/очистку SDK-данных нельзя выполнять над объектом, уже опубликованным в viewer; для изменения нужна собственная копия. Путь задаётся в app, сохранение/хэши используют существующие средства через узкую границу; core/application не получают Qt/OCCT и новый инфраструктурный модуль не вводится до реального потребителя.

## Ключи и угловые случаи

1. **Изменили контур при прежнем артикуле.** Ключ вычисляется по фактическим численным данным после перевода в мм, рабочим/монтажным базам и режиму построения. Имя, путь, mtime и исходный DXF SHA недостаточны. Канонизация не должна округлять геометрию до потери значимых размеров; лишний промах безопаснее ложного совпадения.
2. **Один DXF — несколько ручьёв/контуров.** Учитывать выбранную геометрию/поворот стороны, углы/радиусы/V и параметры условного инструмента, если он используется. Известный DXF и условный клин не делят ключ.
3. **Изменили набор.** Длины/состав/порядок, индивидуальные торцы/ориентации и зазоры входят в ключ набора; одинаковая суммарная длина не означает одинаковую установку. Наличие/количество на складе и цвет сами по себе не меняют геометрию; выбор другого набора по наличию — меняет.
4. **Сменилась посадка/станок.** Монтаж зависит от неизменяемой ревизии станка, держателя/адаптера, выбранных баз/смещений и версии распознавания. Кэш отдельного тела при этом может сохраниться. Перемещение станции по Z и ход пуансона применяются к шаблону отдельно.
5. **Другая деталь/толщина/порядок.** Локальное тело переиспользуется, но координаты детали, контакты и пересечения рассчитываются для нового положения. Консервативные габариты/подготовленные данные могут ускорять проверку, но сохранённое «столкновений нет» от другой детали не переносится. Занятый объём отвода зависит от величины отвода; его нельзя кэшировать только по артикулу.
6. **Проект содержит старую версию инструмента.** Ключ берётся из встроенного снимка `.bend`, а не из текущей записи каталога с тем же названием. Исходного DXF может уже не быть: источник — сохранённый численный контур. Если исчез и он, один кэш по артикулу не заменяет достоверные исходные данные.
7. **Сменились алгоритм, допуски, SDK или качество сетки.** Версии/допуски точного построения входят в ключ тела; параметры триангуляции — в ключ её представления. Меш не подменяет точное тело для Boolean. Изменение цвета/камеры не инвалидирует BRep.
8. **Неполная/повреждённая запись, нет места/прав записи.** Отказ кэша не блокирует обычное построение. Повреждённая запись игнорируется/заменяется; при невозможности записи остаётся работа в памяти, диагностика — в журнале без обязательного диалога. Успешную постоянную запись нельзя заявлять, если запись не состоялась.
9. **Два экземпляра программы.** Нужны атомарная публикация и координация записи по ключу. Готовый immutable-файл не дописывается на месте; временные файлы не принимаются читателем. Отмена задания не публикует частичную запись.
10. **Перенос/обновление программы.** Совместимые данные остаются вне runtime; несовместимые записи пропускаются. Частные профили и производный кэш не включаются в Git, пользовательский ZIP/публичные тестовые ассеты и сетевые запросы автоматически.
11. **Очень простое тело/медленный носитель.** Чтение и проверка файла могут оказаться дороже построения простого клина/параллелепипеда. Политику чтения/сохранения таких тел выбирать по замеру; RAM-hit и применение Location не должны требовать обращения к диску при каждом кадре. Наличие постоянного кэша не означает ускорения любого примитива.

## Реализация и измерения следующего блока

1. Раздельно измерить построение профиля/секций, meshing, сборку станка, кадры детали и Boolean-проверки; выделить I/O и проверку загруженной записи. Без этого нельзя обещать коэффициент ускорения всего переключения.
2. Разделить локальное тело и размещение, доказать эквивалентность текущим мировым телам; проверить прямую экструзию секций. Добавить устойчивый отпечаток фактических входов.
3. Реализовать общий ограниченный RAM-кэш плюс постоянное хранение выбранного формата и восстановление после запуска; использовать один путь для ручного/полного режима. Сравнить отсутствие кэша, RAM-hit и первый disk-hit после нового процесса.
4. Проверить две разные детали с одной оснасткой, обе стороны и симметричный инструмент; ту же метку артикула с другим контуром/масштабом; разные ручьи/длины/зазоры/порядок секций; старый проект; смену станка/SDK/mesh-параметров; повреждённый файл/нет записи/два процесса/прерванную запись. Новый процесс с действительной записью должен восстановить тела без запуска их построителя. Перезапуск ОС проверить отдельно от перезапуска процесса.
5. Сравнить геометрию, объём, положения секций, результаты столкновений и полного/ручного движения с отключённым кэшем. Проверки не становятся положительными из-за самого cache-hit. GPU — только 100%; D051 сохраняется.

Ожидаемый выигрыш относится к подготовке одинаковой оснастки на разных деталях и после перезапуска. Если основное время занимает проверка деформирующейся детали, общий выигрыш будет ограничен этой долей. Сам по себе файл с двумя ориентациями не устраняет эти вычисления. Численный выигрыш пока не измерен; программное поведение не менялось.

## Источники проверки

- Локальный код: DrawingTools.cpp, SingleBendPreviewBuilder.cpp, RouteDraftGeometry.cpp, MachineAssembly.cpp, BendRouteBuilder.cpp, ToolCatalog.h; документация D071/D089/D090/D042.
- [OCCT: BinTools](https://www.occt3d.com/dev/doc/refman/html/class_bin_tools.html) — первичная справка, просмотрена 2026-10-30: сохранение BRep/триангуляции и версия формата. Текущая online-справка относится к 8.0.1, не основание перехода проекта на OCCT 8; наличие нужного API 7.6.3 отдельно сверено по локальным BinTools.hxx/BinTools_FormatVersion.hxx. Реального round-trip постоянного кэша не выполнялось.
- [OCCT: Topology training](https://dev.opencascade.org/sites/default/files/pdf/Topology.pdf) — первичные материалы OCCT о разделяемой топологии и Location/Move/Moved. Повторное использование локального тела согласуется с фактическим кодом ориентации; неизменность данных остаётся обязанностью приложения.
