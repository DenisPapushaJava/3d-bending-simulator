## Изменение alpha.3

В существующей матрице обеих ОС компиляция использует `--parallel 4`, CTest — `--parallel 2`. Core quality остаётся прежним. Публичные стандартные ubuntu-24.04/windows-2022 runners имеют четыре CPU/16 GB RAM по [документации GitHub](https://docs.github.com/en/actions/reference/runners/github-hosted-runners); [CTest](https://cmake.org/cmake/help/v3.28/manual/ctest.1.html#cmdoption-ctest-j) распределяет зарегистрированные тесты между двумя процессами. Локальный полный dev уже проходил 85/85 при двух тестах одновременно; Windows подтверждается новым CI.

Набор/таймауты/масштаб тестов не сокращаются. Теги по-прежнему требуют полного CI, упаковка идёт только после успеха, черновик проверяется перед публикацией. SDK/triplet/Qt/зависимости/VERSION-семантика прежние. Это уточняет прежние два build-потока D155 только для CI; локальные preset release/core остаются с двумя.

## Декомпозиция и дальнейшие варианты

Матрица уже разделяет Windows/Linux, а quality и публикация отдельны. Дополнительное разбиение каждого CTest на отдельный runner потребует повторять установку SDK/Qt или передавать большой runtime между jobs. Сначала измеряется существующая матрица с ограниченным параллелизмом.

Повторные PR/main/tag действительно могут компилировать одинаковый код. Перенос готового проверенного Windows-комплекта между ними потребует отдельного контракта происхождения: точный commit/tree, компилятор/SDK, успешные проверки, неизменяемые артефакты и повторная проверка SHA/манифеста. Сейчас это не реализовано и не используется для пропуска релизных проверок. Кэш успешного отпечатка остаётся прежней оптимизацией, теги его не используют.

Сама упаковка занимает лишь 36 с, SDK — 39 с. Их отдельный универсальный pipeline или новая система кэша сейчас не устраняют главный источник задержки. PCH/кэш собственного компилятора можно измерить позже, если компиляция останется главным этапом после ускорения тестов. Итог нового выпуска фиксируется ниже после CI; обещание ускорения в N раз заранее не даётся.

## Проверки alpha.3

Первый PR-прогон Windows обнаружил C4456 в BendingDrawingBuilder: два локальных имени source затеняли внешнюю CAD-ссылку. Они переименованы в projection без изменения вычислений, строгие предупреждения сохранены. Локально пересобран drawing_tests и пройден сценарий основных проекционных размеров; обе ОС повторяются на исправленном коммите. Числа неуспешной сборки не считаются измерением ускорения успешного выпуска.

Во втором прогоне Linux прошёл **88/88**: compile 168 с, CTest 401 с (против 202/715 с alpha.2). Наборы разных версий не идентичны, поэтому это сравнение полного этапа на hosted runner, не чистый benchmark одного алгоритма. Windows затем обнаружил C4458 у локальной подписи упора title; имя изменено на gaugeTitle. Дополнительно проверены 29 изменённых UI/test единиц компиляции с диагностикой shadow, без записи объектов/dependency files. Конструкторные параметры и отдельные lambda-области GCC проверяет шире MSVC; предупреждения компилятора Windows не отключаются. Финальный полный прогон обеих ОС выполняется после исправления.

Третий Windows-прогон собрал весь код, но ранний сценарий app.bending-drawing выявил некорректный переносимый тест имени: строка A:B?C.stp на Windows содержит диск A:, а не двоеточие в имени. Тест теперь задаёт полный родительский путь и отдельно проверяет абсолютный/относительный префикс диска на Windows; функция сохранения не менялась.

Из-за позднего обнаружения этого отказа CTest разделён на две последовательные фазы в прежнем build-job: сначала cad.step-import, project.portable-file и app.bending-drawing, затем точное дополнение через тот же regex с -E. В каждой фазе j2; наборы не пересекаются и вместе включают все тесты. Успешная упаковка требует обеих фаз. Это ускоряет обратную связь на наиболее изменяемых переносимых сценариях, не сокращает маршрутную/графическую регрессию и не добавляет отдельных runner.

Окончательная упаковка выполняется по тегу и проверяется отдельно.

## Подготовка alpha.4 — переносимость проверок

При полном CI обеих ОС строгие предупреждения сохранены: имена `far` и `updates` уточнены для Windows, параметры конструкторов — для дополнительной проверки `-Wshadow`. Проверены 71 изменённая единица компиляции; алгоритмы не менялись. Тест предела сечений больше не зависит от порядка профилей OCCT: успешная частичная правка обязана присутствовать в результате, а переполнение проверяется набором из 17 явно ручных сечений при прежнем лимите 16.

Linux-прогон выявил ошибочное сравнение камеры: свободная орбита OCCT вращает вокруг своей gravity point и может смещать target. Диагностика показала точные Direction=(1,0,0), Up=(0,1,0) после якоря при изменённом target. Тест сравнивает фронтальные проекции после одинакового FitAll, не требует отмены допустимого смещения свободной камеры; прежний порог ≤2 пикселей, проверки панорамирования/масштаба/кадров и выхода из якоря сохранены. Рабочий viewer не менялся. Локально сценарий прошёл и native Linux/X11, и с LIBGL_ALWAYS_SOFTWARE=1 при 100%. Временная трассировка удалена.

Linux CI заменяет прямые URL `azure.archive.ubuntu.com/ubuntu` на `archive.ubuntu.com/ubuntu` в sources.list/*.sources/*.list при прежних пакетах, pockets и проверке подписей Ubuntu. Локальный install-script Linux Mint не менялся. В PR APT занял 23 с, однако эта замена **не охватывает** новый `mirror+file` / `/etc/apt/apt-mirrors.txt`: на первом runner тега остался Azure. Живой лог и затем сохранённый лог подтвердили 59,4 MB за 24 мин 3 с (41,1 kB/s), повтор `occt-misc`; код ещё не собирался. Это задержка доставки зависимостей, не вычислений CAD.

После успешной Windows-упаковки медленный Linux был отменён и [повторён отдельно вместе с зависимыми задачами](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs?tool=cli). Во второй попытке того же [CI тега 42132173563](https://github.com/DenisPapushaJava/3d-bending-simulator/actions/runs/42132173563) Windows-результат/asset сохранены, Linux прошёл весь набор; CI и создание черновика успешны. Тег, source tree и Windows ZIP не менялись. Доработка mirror-list и ограничение сетевого ожидания остаются отдельным следующим CI-исправлением, не заявляются выполненными.

В alpha.4 API GitHub показал один и тот же ключ успешного CI для PR, main и тега. У PR запись принадлежала `refs/pull/26/merge`. Доступность кэша ограничена этой ссылкой, поэтому main повторно выполнил полную матрицу, а тег по контракту потребовал ещё один полный прогон. [Области доступа к кэшу GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache).

Следующий вариант для проверки — собирать и тестировать Windows-комплект в одном доверенном прогоне кандидата. Тег может публиковать уже проверенный архив при точном совпадении дерева исходников, версии и разрешённого прогона. При переносе архива проверяются его SHA-256, состав и происхождение. Такой вариант убирает повторную работу, а выигрыш по ожиданию зависит от того, какие прогоны и так идут параллельно. Для alpha.5 сохранён действующий CI.
